== Vue 3 -- Corporate React {plus}{plus}

I MEAN the {vue}, not 2 -- a very different animal. Vue 2 {vue2-eol}.
{vue-compiler-informed}, fully {vue-composition-api}, ES6 Proxies -- a solid swap for React in corporate America.
The template compiler leaves patch flags in the generated code, so the runtime diff skips everything static.
One official stack: {vue-router}, {pinia}, and {vite} from Vue's own author.

And I find it easier to teach than React.
`ref()` and `computed()` track their dependencies on their own: no rules of hooks, no dependency arrays to get wrong.
Less ceremony is more work done, as I mentioned in the video.

== SolidJS -- Performance Choice

{solidjs} is an entirely different paradigm -- compiled, no VDOM. I dig! The few SPAs I built with it performed very well.
I could demo Solid in {read-model-site} if page performance were the key. (Still might, tempted...)

Remarkable here is **the 2-stage process**: the compiler turns JSX into real DOM templates with the static HTML pulled out,
then a small runtime of signals updates only the nodes that depend on the changed state.
Components run once -- nothing re-renders, and the DOM-heavy read model stays a little faster.

== Qwik -- Resumable Rendering

Full disclosure: {qwik} is not what I find much use for. +
More and more distributed systems folks now reach for it. +
Because there is a viable use case.

The "new" paradigm here is {qwik-resumable} instead of hydrating the DOM.
And the entire magic is driven by *_lazy loading_*.
Sure, competent engineers use plenty of *_lazy_* where it fits logically.
And here, _everything is lazy_. The key to a perfect {lighthouse} performance score is to use LESS JavaScript.
Colloquial wisdom says that a 20% faster site makes 10% more conversions.
Delayed loading helps on long-funnel landing pages, convoluted and branching page functions,
and optional expensive actions that are not frequently used.

Note: I find myself making a clean feature-centric read model and not needing this.
My architecture tends to avoid all the aforementioned scenarios.
Or perhaps I haven't met the right use case.

== On Frameworks

*_Frameworks are excluded by the apples-to-apples rule!_*

In one of the buildathons I noticed teams comparing a React bench to a {nextjs} bench.
Next.js is a framework built around the same React. So I understood that
unlike in Python or Java ecosystems, JS/TS people say "library/framework" loosely.
Here is what each project calls itself:

[cols="1,3,2"]
|===
|Project |Self-description |Source

|{react} |"the *library* for web and native user interfaces" |react.dev
|{vue} |"progressive, incrementally-adoptable JavaScript *framework*" |{vue-core}
|{solidjs} |"JavaScript *library* for building user interfaces" |{solid-core}
|{svelte} |"It's a *compiler*" |{svelte-readme}
|{qwik} |"*Framework* reimagined for the edge!" |qwik.dev
|{angular} |"The web development *framework* for building modern apps." |angular.dev
|===

{ui-libs-2025-url}[State of JS,window=_blank] files them all under "front-end frameworks."

Angular is indeed a framework! I will define the terms scientifically and build the fixtures
hacka-terrifically another day. You are welcome to join me, and I'll be glad to code with you.
